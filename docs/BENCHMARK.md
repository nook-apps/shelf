# Замеры Shelf

Соберите Release и запустите стенд. Он создаёт временные каталоги, запускает настоящие функции окна Shelf и собирает JSON по каждому прогону. Пользовательские HOME и XDG не используются, а отдельный тест следит, чтобы сохранённая сессия вызывающего процесса не исчезла.

```sh
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DSHELF_TESTS=ON
cmake --build build
python3 tools/bench.py build/shelf --runs 5 \
  --baseline docs/benchmarks/v0.5.1-fedora43.json --output /tmp/shelf-bench.json
```

`--baseline-binary` запускает обе сборки на одном наборе файлов. `--fixture-parent` позволяет выбрать файловую систему для тестовых данных, например внешний диск. Для проверки регрессий на одном компьютере применяйте `--threshold`: он учитывает только изменение медианы более чем на заданный процент и 20 мс. Плановый запуск GitHub Actions использует `v0.6.0` как основу после появления тега и сохраняет JSON в артефакте.

Время первого кадра с файлами, время готовности всей папки и интервалы между кадрами измеряются отдельно. Медиана и p95 относятся к прогонам, а `*_p95_frame_ms` относится к кадрам внутри сценария. Абсолютные цифры зависят от машины, диска и загрузки системы. Программный рендерер offscreen проверяет основной сценарий в CI; для оценки стекла под Hyprland нужен прогон с его композитором.

База 0.5.1 получена из тега `v0.5.1` с тем же стендом и без изменений в файловой модели. Обе серии записаны в `docs/benchmarks/` на Fedora 43, Qt 6.10.3, AMD Ryzen 5 220, с тестовыми файлами во временной файловой системе. RSS измеряется между началом загрузки QML и завершением сценария. Он включает активные вкладки и кэши, поэтому сам по себе не свидетельствует об утечке.

| Сценарий | 0.5.1, мс | 0.6.0, мс |
|---|---:|---:|
| Первый кадр после запуска | 288 | 262 |
| Первые файлы в папке на 50 000 | 778 | 59 |
| Все 50 000 файлов в модели | 778 | 569 |
| Выделить все 50 000 файлов | 12620 | 87 |
| Рамка на 50 000 файлов | 12460 | 75 |
| Сортировка 50 000 файлов | 279 | 45 |
| Чтение 512 сохранённых видов | 2157 | 16 |
| p95 кадра прокрутки | 19 | 24 |
| Худший интервал кадра при зуме | 221 | 30 |

В этом прогоне p95 прокрутки вырос с 19 до 24 мс, хотя худший интервал сократился с 38 до 30 мс. Стенд программного рендеринга не подтверждает, что все кадры укладываются в 16 мс.

`scroll` каждые 47 позиций сразу переносит вид к другому элементу. `wheel_scroll` проходит 60 шагов по 90 пикселей через тот же обработчик смещения, который использует колесо мыши. При парном замере на Fedora 43 в семи прогонах до и после добавления буфера делегатов медиана p95 для прыжков улучшилась с 30 до 23 мс, а медиана худшего кадра выросла с 42 до 53 мс. Для нового сценария колеса p95 составил 17 мс, худший кадр — 23 мс. Эти числа описывают программный рендеринг на ноутбуке. Сравнение колеса с 0.5.1 и замеры на композиторе остаются в #31.
